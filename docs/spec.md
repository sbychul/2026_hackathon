# 기능 명세서 (docs/spec.md)

> 해커톤 팀 프로젝트의 확정 명세. 질문 단계는 이미 끝났고 팀 합의가 끝난 상태다.
> 아래 "가정"으로 표시된 항목만 팀 확인이 필요하다.

## 1. 한 줄 설명

PDF나 텍스트에 들어 있는 개인정보를 브라우저 안에서 자동으로 찾아 가려준다.
기업 사용자는 회사의 하드 룰이 강제로 적용되고, 관리자는 사람별로 어떤 룰에 몇 번 걸렸는지 통계만 본다.

## 2. 핵심 원칙

- 문서와 텍스트의 내용은 브라우저 밖으로 나가지 않는다. 탐지와 마스킹은 전부 브라우저에서 처리한다.
- 서버(Supabase)에 저장하는 것은 "누가, 언제, 어떤 룰에, 몇 번 걸렸는지"뿐이다.
- 파일, 텍스트 원문, 탐지된 실제 값(주민번호 자체 등)은 절대 저장하지 않는다.
- 관리자도 내용은 볼 수 없고 통계만 본다.
- 목적은 처벌이 아니라 보안 교육 대상 파악이다. (발표 때 이렇게 설명한다)

## 3. 사용자 유형

| 유형 | 로그인 | 마스킹 방식 | 탐지 기록 저장 |
|---|---|---|---|
| 기업 직원 | 필요 | 하드 룰 강제 (해제 불가, 탐지되면 무조건 마스킹) | 저장함 |
| 기업 관리자 | 필요 | 직원과 동일하게 사용 가능 | 저장함 |
| 개인 사용자 | 불필요 | 마스킹할 항목을 직접 선택 | 저장 안 함 |

- 가정: 개인 사용자는 로그인 없이 쓰고 기록도 남기지 않는다. (범위를 줄이기 위한 가정)
- 관리자는 대시보드를 볼 수 있는 추가 권한을 가진 기업 사용자다.

## 4. 입력 방식

- 기본 화면의 PDF 업로드: 텍스트가 들어 있는 PDF를 대상으로 한다. 스캔본은 #20의 별도 검증 화면에서 전화번호 가림을 먼저 제공한다.
- 텍스트 직접 입력: 입력창에 붙여넣기 한다.
- 두 방식 모두 같은 탐지 규칙을 쓰고, 같은 방식으로 기록한다.

## 5. 탐지 룰 (코드에 고정)

| 룰 이름 | 대상 | 비고 |
|---|---|---|
| 주민등록번호 | 6자리-7자리 형태 | 오탐 줄이기 위해 앞 6자리 날짜 형식 검사 |
| 전화번호 | 010-0000-0000 등 휴대전화 형태 | 하이픈 유무 모두 허용 |
| 이메일 | 일반 이메일 형태 | |
| 카드번호 | 16자리, 4자리씩 구분 형태 | 룬(Luhn) 체크섬 검증 |
| 이름 | "이름", "성명", "성함" 뒤에 오는 한글 2~4자 | 라벨은 남기고 이름만 가림 |
| 주소 | 시/도로 시작하는 표준 형식 주소 | 도로명(○○로/길 + 건물번호), 지번(○○동/리 + 번지), 뒤의 동·호·층까지 |

- 이름은 문장 속 이름을 정규식으로 구분할 수 없어서, 라벨이 붙은 경우만 잡는다. ("홍길동 님"처럼 라벨 없는 이름은 범위 밖)
- 주소는 시/도 이름으로 시작해야 잡힌다. 시/도를 생략한 주소, 아파트 이름 같은 자유 형식 상세주소는 범위 밖이다.
- 샘플 PDF와 샘플 텍스트의 가짜 이름, 주소는 위 형식에 맞춰 만든다.
- 시간이 남으면 추가: 계좌번호 (숫자 패턴이 흔해서 오탐이 많으므로 후순위)
- 룰 목록은 `rules` 테이블에도 같은 이름으로 넣어두고, 코드의 룰 이름과 일치시킨다.

## 6. 기능 목록

### 6-1. 텍스트 마스킹
1. 텍스트를 입력하면 룰에 걸리는 부분을 하이라이트해서 보여준다.
2. 기업 사용자: 하이라이트된 항목은 전부 마스킹된다. (해제 불가)
3. 개인 사용자: 항목마다 체크박스로 마스킹할지 선택한다. 룰 종류별로 한 번에 선택하는 것도 가능하다.
4. 마스킹된 결과 텍스트를 보여주고 복사 버튼을 제공한다.
5. 마스킹은 원문의 해당 부분을 가림 문자로 바꾼 새 문자열을 만들기 때문에 실제로 복원할 수 없다.

### 6-2. PDF 마스킹
1. PDF를 올리면 페이지 미리보기를 보여준다.
2. 글자와 위치를 읽어 룰에 걸리는 영역을 찾아 표시한다.
3. 기업 사용자: 탐지된 영역은 전부 마스킹된다. 개인 사용자: 영역별로 선택한다.
4. 마스킹된 PDF를 다운로드한다.
5. 중요: 검은 박스만 위에 덮으면 안 된다. 글자가 PDF 안에 남아서 복사하면 나온다. 마스킹한 페이지를 이미지로 구워서 새 PDF로 만들어야 진짜 마스킹이다.
6. 기본 화면과 별도로 #20 첨부 화면에서 사용자가 선택한 PDF에 공통 규칙 6종을 모두 적용한다. 이미지가 있는 페이지에만 5세대 한국어 경량 모델을 사용하며, 원본은 기기 밖으로 보내지 않는다. 개발용 생성 예제나 사전 탑재 파일은 제공하지 않는다. 규칙과 인식의 한계로 빠지는 항목은 사용자가 확인해야 한다.

### 6-3. 로그인 (기업 모드)
- Supabase 로그인을 쓴다. 직원과 관리자는 `profiles.role`로 구분한다.
- 시연용 계정(직원 여러 명, 관리자 1명)을 미리 만들어둔다.
- 로그인한 사용자가 마스킹을 완료하면 탐지 기록을 저장한다.

### 6-4. 탐지 기록 저장
- 마스킹 1번에 룰마다 한 줄씩 기록한다. (걸린 건수가 0인 룰은 기록하지 않는다)
- 저장 항목: 사용자 id, 룰 id, 걸린 건수, 입력 방식(텍스트/PDF), 시각

### 6-5. 관리자 대시보드
1. 가장 많이 탐지된 사람 순위 (전체 건수 기준)
2. 사람별 × 룰별 카운트 표
3. 룰별 전체 합계 그래프
4. 업로드(마스킹 실행) 횟수 순위는 시간이 남을 때 추가한다.
- 내용은 어디에도 보이지 않는다. 숫자와 이름만 나온다.

## 7. 화면 (3개)

1. 로그인 화면: 기업 로그인, "개인으로 사용하기" 진입 버튼
2. 마스킹 화면: 입력 방식 전환(텍스트/PDF), 탐지 결과, 마스킹 결과, 복사 또는 다운로드. 기업 모드는 선택 체크박스가 없고, 개인 모드는 있다.
3. 관리자 대시보드: 순위, 사람별·룰별 표, 룰별 합계 그래프

- 화면 설계는 피그마에서 프론트 담당이 한다. 시안이 나오면 한 화면(프레임)씩 구현한다.
- 시안이 나오기 전에는 로직 모듈(룰, 탐지, 마스킹)부터 만든다.

## 8. 데이터 구조 (Supabase)

- `profiles`: id(로그인 사용자 id), 이름, 역할(직원/관리자)
- `rules`: id, 룰 이름, 켜짐 여부 (처음엔 6개를 미리 넣어둔다. 이름은 코드의 룰 id와 같게: rrn, phone, email, card, name, address)
- `detections`: id, 사용자 id, 룰 id, 걸린 건수, 입력 방식, 생성 시각

### 접근 제한 (행 단위 보안, RLS)
- 직원: 자기 기록만 추가하고 읽을 수 있다.
- 관리자: 전체 기록을 읽을 수 있다.
- 사용자가 자기 역할을 직접 바꾸지 못하게 `profiles`의 역할 수정을 막는다.
- 탐지 기록은 추가만 가능하고, 수정과 삭제는 막는다.

## 9. 기술 방향 (제안)

- 웹 서비스. React와 TypeScript를 제안한다. (팀 합의 시 변경 가능)
- 서버는 직접 만들지 않는다. Supabase(로그인, DB)만 사용한다.
- 이번 범위에는 AI 호출이 없으므로 서버리스 함수도 필요 없다.
- PDF 읽기: pdf.js 계열. 마스킹 후 PDF 저장: pdf-lib 또는 jsPDF 계열. (라이브러리는 구현 시 확정)
- PDF 글자는 조각 단위로 나뉘어 읽히는 경우가 많다. 페이지 단위로 글자를 이어 붙이고, 이어 붙인 문자열의 위치와 원래 글자 조각의 위치를 대응시켜서 탐지 영역의 좌표를 구한다.
- 프론트에는 Supabase 공개용(anon) 키만 사용한다. service_role 키는 절대 사용하지 않는다.
- 환경변수 파일은 `.gitignore`에 포함하고, 커밋 전에 `git status`로 확인한다.

## 10. 우선순위

1. 텍스트 탐지와 마스킹 (가장 쉬우므로 먼저 만들어 흐름을 검증한다)
2. PDF 업로드 → 탐지 → 이미지로 구운 PDF 다운로드
3. 로그인과 탐지 기록 저장, 기업 모드의 하드 룰 강제
4. 관리자 대시보드 (순위, 사람별·룰별 표)
5. 개인 모드의 항목 선택 기능
6. 후순위: 룰별 합계 그래프 꾸미기, 계좌번호 룰, 업로드 횟수 순위, 룰 켜고 끄기

- 4번 대시보드는 가짜 데이터로 화면을 먼저 만들고 나중에 Supabase 연결로 교체한다.

## 11. 범위 밖

- 정밀 글자별 가림과 기본 화면 통합 (#20의 현재 단계는 별도 첨부 화면에서 공통 규칙 6종 적용)
- 파일이나 텍스트 원문의 서버 저장
- 룰 추가·수정 화면 (룰은 코드에 고정)
- 실제 개인정보를 사용한 시연 (샘플 PDF와 샘플 텍스트는 가짜 정보로 만든다)

## 12. 시연 시나리오

1. 개인 모드로 샘플 텍스트를 붙여넣고, 일부 항목만 선택해서 마스킹한다.
2. 직원 계정으로 로그인해 샘플 PDF를 올리면 전부 강제로 마스킹된다. 다운로드한 PDF에서 글자를 복사해도 원문이 나오지 않음을 보여준다.
3. 관리자 계정으로 로그인해 방금 직원의 카운트가 올라간 것을 확인한다. 가짜 직원 5~10명의 기록이 미리 들어 있어서 순위와 표가 채워져 있다.

## 13. 이슈 분류 (GitHub Issues로 쪼갤 단위)

- 프론트: 공통 컴포넌트, 로그인 화면, 마스킹 화면, 관리자 대시보드 화면
- 로직: 룰별 정규식 모음, 텍스트 탐지와 마스킹, PDF 글자 위치 추출, PDF 이미지화와 저장
- Supabase: 프로젝트와 테이블 생성, 로그인 설정, RLS 설정, 가짜 데이터 시드, 탐지 기록 저장 연결, 배포
- 기획: 룰별 탐지 기준 정리, 샘플 PDF와 샘플 텍스트 제작(가짜 정보), 발표 대본, 시연 순서, 테스트

## 14. 발표 때 강조할 점

- 문서와 텍스트는 브라우저 밖으로 나가지 않는다.
- 관리자도 내용은 못 보고 통계만 본다.
- 처벌용이 아니라 보안 교육 대상을 파악하는 용도다.
- 하드 룰은 직원이 해제할 수 없다.
