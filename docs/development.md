# 개발 문서

## 실행

```bash
npm install
npm run dev     # 개발 서버
npm test        # 테스트 (Vitest)
npm run build   # 타입 검사 + 빌드
npm run lint    # 린트 (oxlint)
```

## 구조

```
src/
  rules/rules.ts        탐지 룰 정의 (주민등록번호, 전화번호, 이메일, 카드번호, 이름, 주소)
  masking/detect.ts     텍스트 → 탐지 구간 목록 (위치만, 실제 값은 담지 않음)
  masking/mask.ts       원문 + 선택한 구간 → 가림 문자로 바꾼 새 문자열
```

- 룰 id(`rrn`, `phone`, `email`, `card`, `name`, `address`)는 Supabase `rules` 테이블의 룰 이름과 같게 맞춘다.
- 카드번호는 룬(Luhn) 체크섬을 검사한다. 샘플 데이터의 가짜 카드번호도 체크섬을 통과하는 값으로 만든다. (예: `4111-1111-1111-1111`)
- 화면(`pages/`), 공통 컴포넌트(`components/`), Supabase 클라이언트(`lib/`)는 해당 이슈에서 추가한다.

## 규칙

- 작업 규칙은 `AGENTS.md`를 따른다.
- 파일, 텍스트 원문, 탐지된 실제 값은 서버에 저장하거나 로그로 남기지 않는다.
- `.env`는 커밋하지 않는다. 프론트에는 Supabase 공개용(anon) 키만 쓴다.

## 스캔 문서 전화번호 시연 (#20 첫 단계)

이 단계는 기존 화면과 분리된 검증용 진입점이다. 5세대 한국어 경량 모델로 스캔 문서를 읽고, 프로젝트의 전화번호 규칙을 적용한 뒤 기존 문서 저장 함수를 호출한다. 별도의 문서 처리 서버는 없다.

```bash
npm ci
npm run prepare:ocr
npm run build:ocr-demo
npm run preview -- --host 127.0.0.1
```

브라우저에서 `/src/lib/ocr/demo/index.html`을 열고 가짜 정보가 들어 있는 스캔 문서를 선택한다. 모델 두 개와 실행기는 서비스와 같은 출처의 정적 자원으로 제공한다. `public/models/ocr`를 포함한 빌드 결과를 정적으로 배포하면 된다. 모델을 제공하는 웹 호스팅은 필요하지만 문서 업로드나 서버 추론은 하지 않는다.

### 처리와 데이터 수명

- `scanPdfPhones`: 페이지의 그리기 명령을 검사한다. 이미지가 있는 페이지에만 작업자 추론을 적용하고, 이미지가 없는 페이지는 저장된 글자와 위치를 직접 읽는다. 두 경로 모두 기존 탐지 함수에 전화번호 규칙만 전달한다.
- `BrowserOcr`: 별도 작업자에서 추론하며 문서 처리 완료·취소·실패 시 작업자를 종료한다. 한 쪽의 시간 제한은 3분이다.
- `phoneRegions`: 번호가 포함된 인식 영역 전체를 가린다. 원문 이미지 기준 4화소 여유를 준 뒤 페이지의 기본 배율 좌표로 환산한다.
- `exportMaskedPdf`: 기존 저장 함수를 재사용한다. 모든 페이지를 가린 이미지로 다시 구성하므로 원본 텍스트 층이나 원본 이미지 객체를 복사하지 않는다.
- 선택한 파일, 인식한 글자, 가림 좌표는 기기 메모리에만 둔다. 다른 파일을 선택하면 이전 문서와 표시 내용을 해제한다. 외부 전송·서버 저장·원문 로그는 만들지 않는다.
- 실패 또는 취소한 결과는 다운로드하지 않는다. 번호 0건도 개인정보가 없다는 판정으로 표시하지 않는다.

### 첫 단계의 범위

- 최대 30메가바이트, 100쪽. 이미지가 없는 문서는 모델을 내려받거나 실행하지 않는다. 이미지가 있는 페이지의 미리보기는 두 장까지만 보관해 긴 문서의 메모리 증가를 줄인다.
- 로고처럼 작은 이미지도 모델 대상이다. 이미지 안의 개인정보를 놓치지 않기 위해 단순 크기 기준으로 생략하지 않는다. 텍스트와 이미지가 섞인 페이지는 전체 페이지를 모델로 읽는다.
- 이미지가 없지만 글자를 도형으로 그린 페이지는 직접 추출할 수 없을 수 있다. 읽을 수 있는 글자가 없으면 확인 필요 안내를 표시한다.
- 분석 시간은 모델을 사용하는 페이지 수에 크게 영향을 받지만, 저장은 기존 함수가 모든 페이지를 다시 그리므로 전체 페이지 수에 비례하는 비용이 남는다.
- 스캔 페이지는 문서에 지정된 회전을 잠시 해제해 인식하고, 결과 좌표를 원래 회전이 적용된 저장 좌표로 다시 옮긴다. 미리보기는 인식 방향으로 표시한다. 이미지 자체가 거꾸로 들어 있거나 임의로 기울어진 글자, 손글씨, 세로쓰기, 암호화 문서의 지원은 보장하지 않는다.
- 글자 검출 후처리는 수평 사각형을 사용한다. 파이썬 실험의 회전 사각형·원근 변환 처리와 다르므로 과거 정확도 수치를 그대로 적용하지 않는다.
- 줄을 넘어 나뉜 전화번호, 모델이 잘못 읽은 번호는 놓칠 수 있다. 이름·주소·카드·이메일 등은 이번 시연에서 가리지 않는다.
- 번호와 같은 인식 영역의 제목이나 다른 내용도 함께 가려질 수 있다. 글자별 정밀 가림은 후속 범위다.
- 일반 문서 처리와 기존 입력·결과 화면은 변경하지 않는다. #15·#16 화면 통합과 #20의 나머지 완료 조건은 후속 작업이다.

추론 실행기 배포 방식은 [공식 브라우저 배포 문서](https://onnxruntime.ai/docs/tutorials/web/deploy.html)를 따른다. 사용 모델의 출처·검증값·사용 허가는 `public/models/ocr/README.md`와 준비 스크립트에 기록한다.

### 브라우저 실측 (2026년 10월 31일)

검증 화면의 가짜 예제를 윈도 환경의 크롬에서 직접 실행했다. 브라우저 추론은 단일 연산 스레드를 사용하며 문서당 1회 측정했다. 아래 시간은 분석 완료까지이며, 최종 문서 생성·다운로드 시간은 포함하지 않는다. 모델 및 실행기 캐시 상태가 달라 일반적인 속도나 개선 배율로 해석하면 안 된다.

| 예제 | 직접 읽기 | 모델 사용 | 찾은 전화번호 | 분석 시간 |
|---|---:|---:|---:|---:|
| 텍스트 30쪽 | 30쪽 | 0쪽 | 30건 | 0.4초 |
| 스캔 1쪽 | 0쪽 | 1쪽 | 3건 | 8.1초 |
| 텍스트 29쪽과 스캔 1쪽 | 29쪽 | 1쪽 | 32건 | 5.7초 |
| 스캔 2쪽, 두 번째 쪽에 90도 회전 지정 | 0쪽 | 2쪽 | 6건 | 9.9초 |

- 스캔 1쪽과 혼합 30쪽 모두 실제 다운로드 파일을 다시 열어 검사했다. 각각 3개와 32개의 가림 사각형 내부가 검은 픽셀이며, 텍스트 추출 결과는 0글자, 이미지 객체는 페이지당 1개, 주석은 0개였다. 텍스트 페이지와 이미지 페이지의 결과를 별도로 렌더링해 눈으로 확인했다.
- 회전 예제의 다운로드 결과도 2쪽의 가림 영역 6곳이 검은 픽셀이고 추출 글자가 0개임을 확인했다. 두 번째 쪽을 별도로 렌더링해 회전된 번호 위치와 가림 영역이 일치하는지 확인했다.
- 30쪽 파일은 분석 후 저장에 수분이 더 걸렸다. 모델 생략은 분석 단계의 개선이며, 전체 페이지를 다시 그리는 기존 저장 기능은 별도 병목이다. 백그라운드 탭의 화면 갱신 대기에도 영향을 받을 수 있어 저장 시간 최적화는 #5와 별도로 조율해야 한다.
- 자동 검사에서는 텍스트 100쪽의 모델 호출·페이지 렌더링이 모두 0회이며, 혼합 30쪽에서는 각각 1회임을 확인한다. 이는 추론기를 시험 대역으로 바꾼 분기 검사이고 실제 100쪽 속도 측정은 아니다.
- 예제 생성은 실제 사용자 파일을 요구하지 않는다. 가짜 전화번호만 기기 안에서 만들고 일반 파일 입력과 같은 분석·저장 함수를 실행한다.
