# 개발 문서

## 실행

```bash
npm install
npm run dev     # 개발 서버
npm test        # 테스트 (Vitest)
npm run build   # 타입 검사 + 빌드
npm run lint    # 린트 (oxlint)
```

## 구조

```
src/
  rules/rules.ts        탐지 룰 정의 (주민등록번호, 전화번호, 이메일, 카드번호, 이름, 주소)
  masking/detect.ts     텍스트 → 탐지 구간 목록 (위치만, 실제 값은 담지 않음)
  masking/mask.ts       원문 + 선택한 구간 → 가림 문자로 바꾼 새 문자열
```

- 룰 id(`rrn`, `phone`, `email`, `card`, `name`, `address`, `account`)는 Supabase `rules` 테이블의 룰 이름과 같게 맞춘다.
- 카드번호는 룬(Luhn) 체크섬을 검사한다. 샘플 데이터의 가짜 카드번호도 체크섬을 통과하는 값으로 만든다. (예: `4111-1111-1111-1111`)
- 화면(`pages/`), 공통 컴포넌트(`components/`), Supabase 클라이언트(`lib/`)는 해당 이슈에서 추가한다.

## 규칙

- 작업 규칙은 `AGENTS.md`를 따른다.
- 파일, 텍스트 원문, 탐지된 실제 값은 서버에 저장하거나 로그로 남기지 않는다.
- `.env`는 커밋하지 않는다. 프론트에는 Supabase 공개용(anon) 키만 쓴다.

## 첨부 PDF의 공통 규칙 가림 (#20)

기존 화면과 분리된 첨부용 진입점이다. 사용자가 선택하거나 끌어다 놓은 PDF에 공통 규칙 6종 전체를 적용한다. 스캔 페이지는 5세대 한국어 경량 모델로 읽고, 이미지 없는 페이지는 저장된 글자를 직접 읽은 뒤 같은 공통 탐지 함수를 사용한다. 별도의 문서 처리 서버는 없다. 개발용 생성 예제와 사전 탑재 PDF는 제거했다.

```bash
npm ci
npm run build:ocr-demo
npm run preview -- --host 127.0.0.1
```

브라우저에서 `/` 또는 `/src/lib/ocr/demo/index.html`을 열고 사용할 PDF를 직접 첨부한 뒤 개인정보 찾기를 누른다. 모델 두 개와 실행기는 서비스와 같은 출처의 정적 자원으로 제공한다. `public/models/ocr`를 포함한 빌드 결과를 정적으로 배포하면 된다. 모델을 제공하는 웹 호스팅은 필요하지만 문서 업로드나 서버 추론은 하지 않는다.

`build:ocr-demo`는 모델 준비·검증을 먼저 실행한다. 모델이 없는 새 체크아웃에서는 고정된 공개 배포 주소에서 내려받고, 실행기는 설치된 패키지에서 복사한다. 다운로드나 검증에 실패하면 빌드도 실패한다. 개발 중 모델만 준비하려면 `npm run prepare:ocr`를 사용한다.

추론은 `ort.env.wasm.numThreads = 1`로 고정한다. `ort-wasm-simd-threaded`라는 파일명을 사용해도 이 설정에서는 다중 스레드를 만들지 않으므로 교차 출처 격리 헤더가 필수가 아니다. 이는 [공식 실행 환경 설정 문서](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html)의 단일 스레드 동작을 따른다. 다중 스레드로 변경할 때는 격리 헤더와 공유 메모리 지원을 별도로 검증해야 한다.

### 처리와 데이터 수명

- `scanPdfPrivacy`: 페이지의 그리기 명령을 검사한다. 이미지가 있는 페이지에만 작업자 추론을 적용하고, 이미지가 없는 페이지는 저장된 글자와 위치를 직접 읽는다. 두 경로 모두 기존 탐지 함수에 `RULES` 전체를 전달한다.
- `BrowserOcr`: 별도 작업자에서 추론하며 문서 처리 완료·취소·실패 시 작업자를 종료한다. 한 쪽의 시간 제한은 3분이다.
- 모델은 사이트 접속만으로 받지 않는다. 첫 이미지 페이지를 처리할 때 같은 출처에서 위치 검출 모델 4,819,576바이트와 한국어 인식 모델 13,488,748바이트를 받고, 한 문서의 다음 이미지 페이지에서는 같은 작업자의 모델을 재사용한다. 화면의 진행률은 실제 응답에서 읽은 바이트로 계산하며, 파일 두 개를 받은 뒤의 실행기 준비 단계와 구분한다. 실행기 약 12.36메가바이트와 문자 사전은 진행 막대의 두 모델 용량에 포함하지 않는다. 브라우저 캐시는 배포 응답과 브라우저 정책에 따라 재사용될 수 있다.
- `privacyRegions`: 글자 조각을 읽기 순서로 연결하고 공통 규칙이 찾은 문자열 구간에 겹치는 원래 글자 영역을 가린다. 라벨과 값 또는 주소가 여러 조각으로 나뉘어도 대응되는 영역을 모두 가린다. 같은 영역의 중복 가림은 제거하고 규칙별 건수는 별도로 센다. 원문 이미지 기준 4화소 여유를 준 뒤 페이지의 기본 배율 좌표로 환산한다.
- `exportMaskedPdf`: 기존 저장 함수를 재사용한다. 모든 페이지를 가린 이미지로 다시 구성하므로 원본 텍스트 층이나 원본 이미지 객체를 복사하지 않는다.
- 선택한 파일, 인식한 글자, 가림 좌표는 기기 메모리에만 둔다. 다른 파일을 선택하면 이전 문서와 표시 내용을 해제한다. 외부 전송·서버 저장·원문 로그는 만들지 않는다.
- 실패 또는 취소한 결과는 다운로드하지 않는다. 분석이 정상 완료된 0건 결과는 다운로드할 수 있지만 개인정보가 없다는 판정으로 표시하지 않는다.

### 현재 적용 범위

- 최대 30메가바이트, 100쪽. 이미지가 없는 문서는 모델을 내려받거나 실행하지 않는다. 이미지가 있는 페이지의 미리보기는 두 장까지만 보관해 긴 문서의 메모리 증가를 줄인다.
- 로고처럼 작은 이미지도 모델 대상이다. 이미지 안의 개인정보를 놓치지 않기 위해 단순 크기 기준으로 생략하지 않는다. 텍스트와 이미지가 섞인 페이지는 전체 페이지를 모델로 읽는다.
- 이미지가 없지만 글자를 도형으로 그린 페이지는 직접 추출할 수 없을 수 있다. 읽을 수 있는 글자가 없으면 확인 필요 안내를 표시한다.
- 분석 시간은 모델을 사용하는 페이지 수에 크게 영향을 받지만, 저장은 기존 함수가 모든 페이지를 다시 그리므로 전체 페이지 수에 비례하는 비용이 남는다.
- 스캔 페이지는 문서에 지정된 회전을 잠시 해제해 인식하고, 결과 좌표를 원래 회전이 적용된 저장 좌표로 다시 옮긴다. 이미 가린 미리보기 픽셀도 같은 회전으로 돌려 저장 결과와 방향을 맞춘다. 이미지 자체가 거꾸로 들어 있거나 임의로 기울어진 글자, 손글씨, 세로쓰기, 암호화 문서의 지원은 보장하지 않는다.
- 글자 검출 후처리는 수평 사각형을 사용한다. 파이썬 실험의 회전 사각형·원근 변환 처리와 다르므로 과거 정확도 수치를 그대로 적용하지 않는다.
- 같은 줄의 가까운 숫자·구분자 조각은 공백 없이 연결해 `010-`, `1234-`, `5678` 같은 분리 결과도 탐지한다. 다른 열이나 줄의 조각은 합치지 않는다. 줄을 넘어 나뉜 전화번호, 모델이 잘못 읽은 번호는 놓칠 수 있다. 주민등록번호·전화번호·이메일·카드번호·이름·주소 규칙을 모두 적용하지만 인식되지 않거나 규칙 형식에 맞지 않는 개인정보까지 탐지한다고 보장하지 않는다. 이름 라벨이나 주소의 시·도 표기가 없는 경우 특히 확인이 필요하다.
- 탐지 값과 같은 인식 영역의 제목이나 다른 내용도 함께 가려질 수 있다. 글자별 정밀 가림은 후속 범위다.
- 일반 문서 처리와 기존 입력·결과 화면은 변경하지 않는다. #15·#16 화면 통합과 #20의 나머지 완료 조건은 후속 작업이다.

추론 실행기 배포 방식은 [공식 브라우저 배포 문서](https://onnxruntime.ai/docs/tutorials/web/deploy.html)를 따른다. 사용 모델의 출처·검증값·사용 허가는 `public/models/ocr/README.md`와 준비 스크립트에 기록한다.

### 검토 요청 #29 수정 검증

- 2026-10-31: 모델 두 개와 실행기 두 파일을 배포 원본 경로에서 백업한 뒤 `npm run build:ocr-demo`만 실행했다. 공개 모델 다운로드·검증과 실행기 복사가 성공했고 네 파일 모두 `dist/models/ocr`에 포함됐다.
- 실제 크롬의 로컬 개발 서버에서 격리 헤더 없이 현재 `loadEngine`을 별도 작업자로 실행했다. 페이지와 작업자의 `crossOriginIsolated`는 모두 `false`, `SharedArrayBuffer`는 `undefined`, 실행 스레드는 1이었다. 두 실제 모델에 영값 시험 입력을 넣어 추론 성공을 확인했다. 검출 출력은 `[1,1,32,32]`, 인식 출력은 `[1,40,11947]`이다. 이는 실행 환경 검사이며 문서 인식 정확도 측정은 아니다.
- 회전 90·180·270도에서 분석 함수, 미리보기 회전, 기존 PDF 저장 함수를 연결한 자동 검사를 추가했다. 문서 파서·추론기·캔버스는 시험 대역이며 실제 저장된 PDF의 페이지 크기와 두 경로의 가림 좌표를 비교한다.
- 실제 화면 이벤트 함수를 통해 0건 완료 결과의 다운로드, 다른 파일 선택 후 비활성화, 진행·취소·실패 시 차단을 검사한다. 번호 조각 결합과 다른 열·줄을 잘못 합치지 않는 검사도 추가했다.
- 자동 검사 183개, 코드 검사, 배포 빌드가 통과했다. 기존 16쪽 자료의 저장된 실제 인식 결과에 수정된 탐지 함수를 다시 적용해 전화번호 42건과 전체 탐지 79건이 유지됨을 확인했다. 전체 79건의 정밀도 검증을 의미하지는 않는다.

### 이전 전화번호 전용 단계의 브라우저 실측 (2026년 10월 31일)

검증 화면의 가짜 예제를 윈도 환경의 크롬에서 직접 실행했다. 브라우저 추론은 단일 연산 스레드를 사용하며 문서당 1회 측정했다. 아래 시간은 분석 완료까지이며, 최종 문서 생성·다운로드 시간은 포함하지 않는다. 모델 및 실행기 캐시 상태가 달라 일반적인 속도나 개선 배율로 해석하면 안 된다.

| 텍스트 30쪽 | 30쪽 | 0쪽 | 30건 | 0.4초 |

- 스캔 1쪽과 혼합 30쪽 모두 실제 다운로드 파일을 다시 열어 검사했다. 각각 3개와 32개의 가림 사각형 내부가 검은 픽셀이며, 텍스트 추출 결과는 0글자, 이미지 객체는 페이지당 1개, 주석은 0개였다. 텍스트 페이지와 이미지 페이지의 결과를 별도로 렌더링해 눈으로 확인했다.
- 회전 예제의 다운로드 결과도 2쪽의 가림 영역 6곳이 검은 픽셀이고 추출 글자가 0개임을 확인했다. 두 번째 쪽을 별도로 렌더링해 회전된 번호 위치와 가림 영역이 일치하는지 확인했다.
- 30쪽 파일은 분석 후 저장에 수분이 더 걸렸다. 모델 생략은 분석 단계의 개선이며, 전체 페이지를 다시 그리는 기존 저장 기능은 별도 병목이다. 백그라운드 탭의 화면 갱신 대기에도 영향을 받을 수 있어 저장 시간 최적화는 #5와 별도로 조율해야 한다.
- 자동 검사에서는 텍스트 100쪽의 모델 호출·페이지 렌더링이 모두 0회이며, 혼합 30쪽에서는 각각 1회임을 확인한다. 이는 추론기를 시험 대역으로 바꾼 분기 검사이고 실제 100쪽 속도 측정은 아니다.
- 예제 생성은 실제 사용자 파일을 요구하지 않는다. 가짜 전화번호만 기기 안에서 만들고 일반 파일 입력과 같은 분석·저장 함수를 실행한다.

### 이전 전화번호 전용 단계의 기존 자료를 합친 다쪽 문서 검증 (2026년 10월 31일)

화면에서 생성하는 예제와 별도로, 기존 `가짜 샘플(이미지X)` 폴더의 01~08번 PDF와 `가짜 샘플(이미지O)/언어2_한국어`의 PDF 8개를 사용했다. 원본 페이지를 바꾸지 않고 글자 페이지와 스캔 페이지를 번갈아 합쳐 16쪽으로 만들었다. 글자 8쪽만 합친 문서도 따로 검사했다.

브라우저 확장의 자동 파일 선택 권한 문제를 피하기 위해, 선택한 기존 파일만 임시 로컬 시험 경로에 복사하고 검증값을 대조했다. 그 바이트로 파일 객체를 만들어 실제 파일 입력 요소의 변경 이벤트에 전달한 후 동일한 분석·다운로드 버튼을 실행했다. 이 검사는 실제 문서 바이트와 앱의 파일 변경 처리부터 저장까지를 검증하지만, 운영체제 파일 선택창 조작 자체를 검증한 것은 아니다. 시험 자료는 저장소나 외부 서버에 올리지 않았다.

### 모델 다운로드 과정 확인

실제 수신량 표시를 검증하기 위해 다른 로컬 출처에서 캐시를 사용하지 않고 모델 파일의 전송 속도만 제한했다. 진행률을 타이머로 흉내 낸 것이 아니라 실제 두 모델 파일을 조각별로 전송한 것이다. 시험 화면에는 속도 제한 시연임을 명시했다. 일반 배포 빌드에는 이 전송 제한이 없다.

- 사이트 접속 직후에는 모델·실행기 요청이 0건이었다. 16쪽 문서의 첫 이미지 페이지인 2쪽에서 두 모델, 문자 사전과 실행기 요청이 발생했다.
- 위치 검출 모델은 약 4.82메가바이트, 한국어 인식 모델은 약 13.49메가바이트를 실제로 받았고, 진행 중·파일 받기 완료·모델 준비 완료를 구분해 표시했다.
- 응답 조각별 진행률, 압축 응답 길이와 실제 모델 길이의 구분, 불완전한 파일 및 오류 응답 거부를 포함한 자동 검사 42개와 검증 화면 빌드가 통과했다.
- 새로 받은 모델로 같은 혼합 16쪽을 다시 처리했으며 직접 읽기 8쪽·모델 사용 8쪽·전화번호 42건과 페이지별 정답 값이 일치했다. 모델 요청은 문서 전체에서 파일별 1회씩, 합계 18,308,324바이트였다. 이 재실행의 135.0초에는 캡처용으로 제한한 모델 전송 시간이 포함되므로 앞의 일반 처리 시간과 비교하지 않는다.
